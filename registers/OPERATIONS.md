# Operating the registers

**What this file is.** The operator loop: who does what, when, to keep the registers and everything derived from them current. The *what and why* of the method is [[METHODOLOGY]]; this file is the *when*. It exists because the machine enforces everything except its own cadence — the gates make counts un-driftable and receipts un-fakeable, but nothing in a gate decides when a candidate is reviewed or when the public copies refresh. Adopted 2026-08-22 (D-110 states the decay window this file exercises).

## Where everything lives — canon and its derived surfaces

One source of truth, four derived surfaces. **Canon is edited; surfaces are derived. Never the reverse.** A defect found on a surface is fixed in canon and re-derived — a surface/canon mismatch is a defect in the surface.

| Surface | Lives at | Derivation | What keeps it honest |
|---|---|---|---|
| **Canon** | `registers/` — the six register files, `README.md`, `METHODOLOGY.md`, this file | — | `check-registers.py` (row data, counts, vocabularies, evidence markers re-derived from receipts) |
| **Web pages** | `content/hub-and-spokes/live/` — the hub and six spoke pages, edited in place, pushed to scale100.co | Prose written from canon, not copied | `check-content-counts.py` (every stated count checked against canon); `check-spoke-evidence.py` (every "Recorded" traces to a lodged mapping) |
| **Public repository** | `public-repo/repo/` staging; published at `github.com/scale100/false-floors` | Registers, `METHODOLOGY.md`, this file, the tool and the checkers **copied from canon at publish time** — never held as a standing second copy (the C-25 stale-canon class) | Both checkers run *after* the copy; `check-content-counts.py --root public-repo` in CI |
| **Trust-check tool** | `tools/trust-check-v1/` | Generated by `extract-registers.mjs` from committed canon | `check-registers.py` compares the view's content stamp (`canonBlobs`) against canon on every run |
| **Figma frames** | HullKey UI Kit file, node IDs in each register's frontmatter | Re-derived by hand from canon | The register frontmatter names the frame revision; frames are currently behind canon and say so — a frame is never the lookup |

Change control is the gates plus review, not a role: canon changes ride a branch, all checkers green (they run in CI via `agent-trust-registers.yml`), Sholto merges. Derived surfaces are never edited to say something canon does not.

## The four cadences

### 1. Event-driven — incidents, as they happen (no schedule)

Exactly the standing practice; nothing new to remember:

- An incident is lodged in the [[../Corrections Register|Corrections Register]] via the fail-fix pipeline; it gets an `⟪instance-of⟫` mapping to the row(s) it instantiates, or an explicit no-fit (recorded — a refused mapping is discrimination evidence).
- Promotion is automatic in effect: once the mapping lands, `check-registers.py` fails until the row's Evidence cell reads `evidenced` and the counts follow. The gate does the bookkeeping enforcement; the operator just lodges honestly.
- A new failure class with no row goes through `--propose-row` (the C-31 miss-reason gate) before any ID is minted.

### 2. Weekly — public-intake triage (starts when the repository goes public)

The repo README promises public triage verdicts, so publishing creates this duty. One pass, ~30 minutes, agent-assisted:

- Sweep new issues (`incident`, `question`, `register correction` templates) and `incidents@scale100.co`.
- Each incident gets a triage label (the verdict is public) and, if real and in scope, enters the event-driven loop above. Questions get answered, not lodged. Register corrections are assessed against the row they cite.
- The reporter is credited on the row if their incident evidences it (credit-on-row, D-102).

### 3. Quarterly — the review point (aligned to the update cadence the hub promises)

Three jobs in one sitting, in this order:

1. **Candidate decay review (D-110).** Every `candidate` row is assessed: any first-party instance, corpus match or filed field case since last review promotes it (the gate will have forced most of these already). A candidate with nothing, for the second consecutive window, is assessed for retirement to the candidate pen using the D-106 retirement test — assessment with a written reason, never a mechanical purge. **The first review is the corpus harvest** (METHODOLOGY section 7, item 1), due with the first quarterly cycle.
2. **Prediction record recompute.** Per METHODOLOGY section 4's definition, from incident dates, mechanically. Publish the updated numbers.
3. **Framework review.** A dated review in `framework-reviews/` in the style of review 02 — what moved, what decayed, what the quarter's incidents say about coverage — feeding the published quarterly update.

### 4. Per-publish — the preflight (any time a derived surface refreshes)

1. All canon edits committed; `check-registers.py` and its `--self-test` green; `check-content-counts.py` and its `--self-test` green; `check-spoke-evidence.py` green on the live spokes.
2. `node tools/trust-check-v1/extract-registers.mjs` regenerated **after** the canon commit, committed, and `check-registers.py` green again (the content stamp check).
3. For a repository publish: copy canon into `public-repo/repo/` (registers, `registers/README.md`, `METHODOLOGY.md`, this file, `register-data.json`, the tool page, the checkers), then run both checkers **after** the copy, then the staging index's own checklist.
4. Link sweep: no `[LINK]` placeholder ships on a published surface.

## What is deliberately not here

No monthly cadence, no dashboards, no standing meetings. A solo operator with agents runs event-driven lodging plus one quarterly checkpoint; anything heavier would be ceremony the gates already make unnecessary. If a duty in this file stops being executable in the time stated, the fix is to shrink the duty or build a check — not to let the file decay into aspiration (the C-31 lesson applies to this file as much as any rule).
