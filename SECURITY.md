# Reporting privately

Most failures can be described in public, and the [public tracker](../../issues) is the better channel when they can – the thread is how you find out what happened to your report, and other people learn from it.

Use the private channel when the failure cannot be described without something you should not post: customer or client names, credentials or tokens, internal hostnames or architecture, proprietary code, or anything under an agreement that stops you sharing it.

**Email:** `incidents@scale100.co`

Include what you would have put in a public report: what you asked for, what the agent did, how you found out, and what caught it if anything did. Redact whatever you need to. A redacted report is far more useful than no report.

## What happens to it

- It is read by a person, not a pipeline.
- Nothing identifying is published. If it produces a catalogue entry, the entry describes the failure in general terms, with no detail traceable back to you or your organisation.
- You are credited by name or handle only if you ask to be. The default is not credited.
- You get a reply with the same verdict a public report would get: new entry, already catalogued with a mechanism, already catalogued with nothing that catches it, or not an instance.

## This is not a vulnerability disclosure channel

This catalogue is about agents failing at their work, not about attackers. If you have found a security vulnerability in a vendor's product, report it to that vendor. If you have found one in the code in this repository, this address is the right place to send it.

## No obligations either way

There is no bug bounty, no service level, and no confidentiality undertaking beyond what is written above. Equally, nothing here asks you for one. If you need a formal agreement before sending anything, say so in a first email with no detail in it.
